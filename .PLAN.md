  * ## Ticket: [future] Advanced Calendar service: one request per event, extended-property tag {#152}

        status: future
        created: 2026-09-26 23:19:15 UTC
        updated: 2026-09-27 00:19:04 UTC

    Not scheduled. Replace CalendarApp calls in the GCal adapter with the
    Advanced Calendar service (Calendar API v3 via the manifest's
    enabledAdvancedServices): insert/patch with attendees, colorId,
    transparency, reminders and a private extendedProperty for the key in one
    request, list with privateExtendedProperty filter instead of scanning and
    reading tags. Expected 5 to 6 times faster exports. Keep the plan layer
    unchanged; only 50_calendar.js changes. Consider batching later.
    Pros and cons of the Advanced Calendar service (Calendar API v3) versus
    CalendarApp, for the decision when this is picked up.

    Pros:
    - One request per event: insert/patch/delete carry summary, description,
      start/end, colorId, transparency, attendees, reminders and
      extendedProperties together; today's ~6 round trips per created event
      become 1, roughly a 5x faster export and clean.
    - Server-side selection: events.list with privateExtendedProperty
      (rotalator=<key>) plus timeMin/timeMax returns only our events, so no
      scanning and tag-reading of every event in the window; a fields mask
      fetches only what the diff compares.
    - Explicit notification control: sendUpdates=none|all|externalOnly on
      insert, patch and delete (CalendarApp offers only sendInvites on create).
    - All-day events use plain `date` strings, removing the script-time-zone
      hazard entirely; timed events use RFC3339 with an explicit timeZone.
    - reminders.useDefault is explicit, so "keep calendar defaults" is a flag
      rather than "do not touch".
    - Batch HTTP (up to 50 operations per request via UrlFetchApp with
      ScriptApp.getOAuthToken) is possible later for another large speedup.
    - Private extended properties are a documented, queryable tag store;
      CalendarApp tags are opaque.

    Cons:
    - Setup: the service must be enabled in the manifest
      (dependencies.enabledAdvancedServices) and, for organisations that
      restrict the default Google Cloud project, a standard GCP project with the
      Calendar API enabled may be required. This adds a step to the "paste one
      file" story and may need an admin in corporate tenants.
    - Quotas and throttling: the API has per-project and per-user rate limits
      (403 rateLimitExceeded / 429); large exports need exponential backoff and
      the run guard must account for retries. CalendarApp hides this behind its
      own lower, opaque quota.
    - Error surface: failures arrive as HTTP errors with JSON bodies to parse;
      CalendarApp errors are friendlier and need no retry logic.
    - More code and a REST-shaped mock: the adapter is a rewrite (~150 lines)
      and the test mock grows; keeping both CalendarApp and v3 paths would
      double maintenance, so it must be a full switch.
    - Migration: events tagged through CalendarApp must be re-tagged or
      recreated once (a one-time Re-export after Clean, or a migration that
      reads tags and writes extended properties).
    - Concurrency semantics change: etags/If-Match are available but add
      another failure mode to handle or ignore deliberately.
    - Batch requests need manual multipart bodies and per-part error handling;
      worthwhile only if single requests are still too slow.
    - Same OAuth scope, so no change in permissions, but the Advanced service
      autocompletion and documentation in the editor are weaker than
      CalendarApp's.

    Recommendation when picked up: full switch of 50_calendar.js to v3 with
    backoff, keep the plan layer unchanged, provide the tag migration through
    Re-export, document the GCP-project caveat in INSTALL, defer batching.

        status: done

    Implement in `src/00_util.js` as plain functions or a `Util` namespace
    object. Unit tests in `test/util.test.js`.

    Datetimes (DESIGN 3.3, 4): represent instants as integer minutes since
    1970-01-01T00:00 with the wall clock treated as UTC. `parseDateTime(text)`
    accepts `YYYY-MM-DDTHH:MM`, `YYYY-MM-DD HH:MM`, `YYYY-MM-DD` (00:00);
    returns null on anything else, including out-of-range fields.
    `formatDateTime(min)` returns canonical `YYYY-MM-DDTHH:MM`.
    `parseDate(text)` for holidays, `YYYY-MM-DD` only. Helpers: day index of
    an instant, weekday, start of day.

    Durations: `parseDuration(text)` for chained `Nw Nd Nh Nm` tokens like
    `1w`, `3d`, `12h`, `1d12h`, `90m`; returns minutes or null. `parsePeriod`
    accepts only `w` and `d`. `formatDuration(min)` produces the shortest
    chained form.

    Lists (3.3): `splitList(text)` splits on `,` or `;`, trims, drops empties.
    `parseAssignments(text)` returns items `{ name, op, value }` with `op` in
    `=`, `+=`, `-=`, or none; value is the raw string; names must not contain
    `=` or `+`. Returns an error string for malformed items.

    `fnv1a32(string)` returning an unsigned 32-bit integer.

    CSV: `parseCsv(text)` and `formatCsv(rows)` handling quotes, embedded
    commas, quotes and newlines, CRLF input. Used by the Node adapter and
    fixtures only, but lives here so it has no imports.

        status: done
        created: 2026-09-22 12:48:09 UTC

    Implement in `src/40_scheduler.js`. Tests in `test/scheduler.test.js`.
    This is DESIGN section 5 end to end for one or many rotations.

    API:
    - `advance(ledger, holidays, now)` returns the snapshot instant `S` per
      DESIGN 5.2 (shift containing now, else grid floor of now, raised to
      anchor, first roster row, existing snapshot).
    - `regenerate({ rotations: [{ name, rows, snapshotAt }], holidays,
      links: [] })` returns `{ rotations: [{ name, rows }], errors, status }`
      where `status` has per-rotation roster scores at `S` and projected at
      horizon end, plus warnings. Pure: no clock, no randomness.

    Steps inside regenerate, per DESIGN 5.3 to 5.8: drop `error` rows; prune
    unpinned shifts with start > S; sort; compute claims and uncovered spans
    from `regenStart` (claim end of the shift at S, else S) to `horizonEnd`
    (grid ceil of S + horizon); split spans at grid boundaries into slots;
    pre-credit pinned shifts in `(S, S + precredit*period)`; sweep all
    rotations' items merged by start with ties by rotation order then type
    order; replay begins at the previous snapshot with `set` rows from the
    top and clipped intervals; record the new snapshot when passing S;
    selection per DESIGN 5.7 with symmetric min_distance, tolerance band,
    `order` and `shuffle` tiebreaks, gradual relaxation of min_distance,
    nobody plus `error` row when unassignable, relaxation note on generated
    shifts. Output rows sorted, old snapshot replaced, no explicit end on the
    last row.

    Validation errors from 10_model and stateful errors from 30_state make
    regenerate return the input rows unchanged plus `error` rows placed at
    the offending row's start with the message, and skip everything else.

    Tests must include: idempotence (regenerate twice gives identical rows);
    determinism of shuffle across runs and its change with seed; fill shift
    after a pinned substitution; pin inside and outside the precredit window;
    exclusion honoured, min_distance relaxed with note; team diff with
    baselines; period change via `set` realigning the grid; unassignable
    slot; advance placement in each of the five cases of DESIGN 5.2.
